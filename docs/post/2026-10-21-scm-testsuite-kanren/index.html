(aux kanren arith): the arithmetic relations of The Reasoned Schemer

Arithmetic as a relation

Chapters 7 and 8 of The Reasoned Schemer, Second Edition build addition, subtraction, multiplication, division, exponentiation and the logarithm out of two truth tables and a great deal of unification. The definitions in (aux kanren arith) are that development, translated line by line into the (aux kanren micro) idiom and then exercised here, with a dozen relations added that the book has no use for -- four mirrored comparisons, then multiple°, divisor°, even°, odd°, square°, composite°, between°, common-divisor°, numeral° and prime°, each a few lines over what chapters 7 and 8 already give. Nothing in the translation is clever: defrel becomes define-relation, conde becomes cond°, fresh becomes fresh°, == becomes =°, (run n (q) g ...) becomes (μkanren-run (q n #t) g ...), and the book's trailing o -- the mark that a name denotes a relation rather than a function -- becomes the trailing ° this repository uses for the same purpose. So addero is adder°, *o is *°, logo is log°. The two relations null° and cons° are not redefined here; they already live in (aux kanren micro).

The numeral

A number is a list of the bits 0 and 1, least significant first, with zero written as the empty list and with no trailing 0. Two is (0 1), five is (1 0 1), six is (0 1 1) and nine is (1 0 0 1). build-num is the only function in the module -- everything else is a relation -- and its quotient recursion stops at zero?, which is what guarantees the absence of a trailing zero. That canonicality is not cosmetic: it makes the encoding injective, so one number has one term, and a term that unifies with (0 0 1) is four and cannot be anything else.

Little-endian is what makes the whole system run in every direction. Addition consumes its arguments from the low bit up, so adder° can peel one cell off each addend and recur without knowing how long either list is -- and the very same clause, read with the sum ground and an addend fresh, subtracts. There is no mode declaration anywhere in the module and no guard on which argument happens to be known. minus° has no body beyond (plus° m k n); division by *° is the multiplication goal with the product ground; factorisation is the same goal with both factors fresh; and (exp° b 2 9) is an integer square root only because exp° is log° with the remainder pinned to '(). Termination in those backward directions is bought, explicitly, by the length guards -- pos°, >1°, <l°, bound-*° -- and the cases below are written to pin exhaustion, not just correctness: a query that asks for more answers than exist asserts that the stream closes.

Goal construction and δ°

In (aux kanren micro), and°, or° and cond° are macros that expand into calls to the procedures andª and orª -- so every goal sub-expression of every clause is evaluated while the goal tree is being built, long before any substitution exists to search over. That used to be the one respect in which the translation could not be literal: define-relation expanded to a plain define, so a recursive call sitting next to other goals in a conjunction was built while its caller was, building the tree for adder° built the tree for adder°, and the first query reaching it never returned. Now define-relation is inverse-η-delayed, exactly as the book's defrel: calling a relation only returns a λ that builds the body when it is applied to a state, and then suspends. No call site needs a hand-written delay to terminate any more.

The module still carries the explicit delay it once needed, an eta-expansion around a δ:

(define-syntax-rule (δ° g) (μ s (δ (g s))))

((=° 1 b) (=° '() m) (δ° (adder° 0 n '(1) r)))

Three self-calls of adder° wear it: the two that discharge a carry against an empty addend and the one that commutes '(1) into the first position; (aux kanren date) wraps its recursive calls the same way. Around a relation made by define-relation the wrapper is redundant for termination. It is kept because removing it drops a suspension, which can shift where answers of a disjunction interleave -- the expectations below were read off runs with the wrappers in place. It is still required around a goal-returning procedure written with a plain define, which nothing delays.

Reading the expected values

Every expectation below was read off a real run. The third argument of μkanren-run is the grounding flag, and it is #t throughout: a variable the search never had to instantiate is reified as a Greek letter in order of appearance, so (α 1) is a single answer standing for both 2 and 3, and (α . β) is pos° and nothing more. Those partially ground answers are the interesting ones -- they are the relation declining to decide a bit it was never asked about, and an expectation that spelled a concrete bit there would be asserting something the code does not claim. Answer ORDER is asserted too: cond° disjoins by INTERLEAVING its clauses, and for a truth table -- where every clause yields exactly one answer -- the interleaving coincides with textual order, so that order is observable ten definitions later in the order plus° hands back its solutions. Where a clause yields more than one answer the two part company, and the expectations below are read off the interleaving.

The definitions under test are a module, (aux kanren arith), rather than a preamble to this suite: the arithmetic is worth importing on its own, and keeping it out here means a case cannot quietly depend on a definition it also supplies. The #;-commented alternatives -- the frame 7:12 half-adder, the frame 7:15 full-adder, and the two flawed /°s of frames 8:54 and 8:64 -- are kept because several cases below exist precisely to say what the surviving definition does that the discarded one does not.

test/car°+cdr°: pass

car° and cdr° are not accessors: each is the one constraint (=° (cons a d) p) projected onto a different variable, which is why the same relation runs backwards and (car° q 'x) answers with the invented pair (x . α) -- a fresh tail, reified as a Greek letter, rather than a failure for lack of input.

Both fail on '(), since no substitution unifies the empty list with a cons cell. That is a contract and not an accident: it is why append° has to test null° in its first clause instead of letting the cdr° chain run out on its own, and it is the same reason pos° and >1° downstream can be written purely as shape unifications.

null° and cons° come from (aux kanren micro), not from (aux kanren arith), so the first two assertions pin the library shapes everything else is built on. If cons° ever stopped being (=° c (cons a d)), every (=° `(,a . ,d) n) in chapters 7 and 8 would still compile and would quietly mean something else.

(define (test/car°+cdr° _)
  (⊦= '(()) (μkanren-run (q 3 #t) (null° q)))
  (⊦= '((1 (2 3)))
      (μkanren-run
        (q 3 #t)
        (fresh° (a d) (cons° a d '(1 2 3)) (=° q (list a d)))))
  (⊦= '(a) (μkanren-run (q 3 #t) (car° '(a b c) q)))
  (⊦= '((b c)) (μkanren-run (q 3 #t) (cdr° '(a b c) q)))
  (⊦= '((1 2 3))
      (μkanren-run
        (q 3 #t)
        (fresh° (a d) (car° '(1 2 3) a) (cdr° '(1 2 3) d) (=° q (cons a d)))))
  (⊦= '((x . α)) (μkanren-run (q 3 #t) (car° q 'x)))
  (⊦= '((α y z)) (μkanren-run (q 3 #t) (cdr° q '(y z))))
  (⊦= '() (μkanren-run (q 3 #t) (car° '() q)))
  (⊦= '() (μkanren-run (q 3 #t) (cdr° '() q))))

test/append°: pass

Three directions of one relation. Forward it concatenates; with the second argument fresh it subtracts a known prefix; with both inputs fresh and the output ground it enumerates the four ways to cut (a b c) in two, both empty-side boundaries included. That third query asks for nine answers and gets four: the assertion is that the search is exhaustive AND terminates, which a spot check for one split would not catch.

The fourth query runs the generator direction, output fresh, and it does not terminate on its own -- it is the count that stops it. Each answer is one cons longer and the still-fresh elements appear as the same Greek letters in x and y, showing they are shared cells and not independent unknowns. That is exactly the shape exp2° leans on when it calls (append° b `(1 . ,b) b2) to double the width of a ground b.

The last case demands a prefix longer than the whole list and gets no answers. A function would have to err or truncate; a relation just has an empty answer stream, and pinning that here is what lets the arithmetic built on it treat failure as ordinary arithmetic information.

(define (test/append° _)
  (⊦= '((a b c d)) (μkanren-run (q 3 #t) (append° '(a b) '(c d) q)))

  (⊦= '((() (a b c)) ((a) (b c)) ((a b) (c)) ((a b c) ()))

        (q 9 #t)

test/bit-xor°+bit-and°: pass

Both truth tables in full, all four rows each, asked with a count of nine so that a fifth answer or a missing row would fail the case. These two relations are the entire arithmetic content of chapters 7 and 8 -- everything preceding them in the module is plumbing -- so a single transposed row would come back as a wrong sum ten definitions later, with nothing local to blame.

The answer ORDER is asserted too, and the two tables do not share it: upstream writes bit-and° as 00, 10, 01, 11 while bit-xor° is 00, 01, 10, 11. Each clause of these tables yields exactly one answer, so cond°'s interleaving degenerates to textual order here; that order is observable and it feeds into the order in which adder° and *° enumerate their solutions, which past the leaves is an interleaving and no longer clause order.

Run backwards from r, bit-xor° has two preimages and bit-and° has one; that asymmetry is what makes the carry bit the deterministic half of half-adder°. The final case feeds a non-bit 2 and gets nothing: the tables are closed, so these relations reject as well as generate, and a malformed bit list dies at the leaf instead of producing a plausible-looking number.

        (q 9 #t)

test/half-adder°: pass

The whole table, derived rather than written: half-adder° is just bit-xor° conjoined with bit-and°, and the enumeration order it produces is bit-xor°'s (00, 01, 10, 11), the first conjunct driving the search while the second filters. The #;-commented alternative from frame 7:12 spells the same four rows out as a table; keeping this case honest is what would expose a divergence between the two.

The last three queries run it backwards, from the outputs to the inputs, which only works because the sum and carry are related by unification and not computed: given r=0 and c=1 there is exactly one input pair that generates a carry, given r=1 and c=0 there are two, and r=1 with c=1 has none at all.

That empty answer is the point of the case. It encodes the invariant x + y = r + 2c, whose maximum is 2, so a sum bit and a carry bit can never both be set. A table with one wrong carry would still answer every forward query plausibly and would only show up as an impossible pair becoming possible here.

test/full-adder°: pass

All eight rows of the table version -- the one the module keeps live because the half-adder°-based definition of frame 7:15, kept #;-commented beside it, costs three sub-goals per bit. This is the leaf of every addition, subtraction, multiplication, division and logarithm in the rest of the module, so it is the one table worth asserting exhaustively, count of seventeen and all.

The next three queries invert it on the output pair, and together they partition the eight rows by how many of b, x, y are set: three ways to reach (r c)=(1,0), three to reach (0,1), exactly one to reach (1,1), and the unlisted (0,0) is the all-zero row. That is b + x + y = r + 2c read off the answer counts, and it is the invariant gen-adder° assumes when it threads e into the next bit position.

The last case pins b=0 to the half-adder table: the same four rows, as they must be, but in a different ORDER, because the clause order of this table is bit-and°-shaped (00, 10, 01, 11) while half-adder° inherits bit-xor°'s. The two relations are extensionally equal and operationally distinct, and it is the operational half that decides the order in which plus° hands back its solutions.

test/pos°: pass

pos° inspects no bits. Its body is the single unification (=° `(,a . ,d) n), so what it actually decides is "n has a car", and it decides it in constant time with no choice point. That it also means n > 0 is a property of the encoding, not of the relation: build-num sends zero, and only zero, to a term without a car.

The last three lines mark exactly where the two readings come apart. (0) is a non-canonical zero -- build-num never emits it -- and pos° says yes; the improper pair (1 . 2) is not a numeral at all and it says yes too; only an atom, with no car to take, fails. So pos° is a structural guard and nothing more, and the obligation to keep non-canonical junk out of it belongs to its callers -- adder°, *°, split° -- which only ever hand it a cdr of a numeral they built themselves.

test/adder°: pass

The carry b is a bit, not a numeral: (adder° 1 n m r) is n+m+1, and the two clauses that consume a set carry against an empty addend discharge it by rewriting it into the literal '(1) and recurring with b back at 0 -- which is why 7+0 with a carry is answered by the same code path as 7+1, and why (adder° 1 '() '() r) bottoms out at '(1). Those two self-calls, together with (adder° b '(1) n r), are exactly the calls this file wraps in δ°: they are clause-level conjuncts of a cond°, which this port once had to delay by hand; since define-relation delays every relation, the wrappers only pin the interleaving, they no longer decide termination. The last two lines ground the sum and leave the carry fresh: the bit is recovered, uniquely, from 3+4 against 8 rather than 7.

(aux kanren date): relations over instants in time

An instant is a numeral, and nothing else

A date, in (aux kanren date), is a POSIX time -- the count of seconds since 1970-01-01T00:00:00Z -- held as the little-endian bit list that build-num produces in (aux kanren arith). Not a record, not a tagged vector, not a new datatype: the SAME canonical numeral, so that every relation of that module already applies to an instant and this one contributes names and a calendar rather than a representation. '() is 1970-01-01T00:00:00Z, and it is a FLOOR and not an origin -- the numeral is unsigned, so there is nothing underneath it and no instant before the epoch can be named at all. That single decision is what the whole module is arranged around, and the cases below are arranged around its consequences.

The consequences were MEASURED, at the magnitudes a date query actually uses, and they are not symmetric. A current instant such as 1760000000 is a 31-bit numeral; 86400 is 17 bits; a day-count since the epoch is 15. At 31 bits <°, <=°, plus° and minus° cost a handful of milliseconds and run in every direction, while *° costs seconds and /° of an instant by 86400 NEVER FINISHED -- it was killed after TEN MINUTES. That is not a performance note. It is the statement that the calendar cannot be reached by relational division, so a design that tries is not slow, it is broken.

Layer 1 is pure; everything calendrical is guarded

So the module is two halves with an explicit boundary, and the cases below are grouped to make that boundary visible. Ordering, durations, shifts and bounded enumeration are PURE relations -- before°, after°, same-instant°, elapsed°, shift°, within°, stride°, stride/≤°, span° -- with no project° anywhere between the caller and the answer, no groundness precondition, and every mode available. elapsed° and shift° are one goal, (plus° t d u), read from different sides; running it backwards is how subtraction is spelled, because the module contains no subtraction of its own.

Calendar conversion is the other half, and every relation in it is project°-GUARDED: it reads the substitution when the goal runs, and where the relevant side is ground it escapes to Scheme -- Howard Hinnant's days-from-civil / civil-from-days, integer-only and table-free -- and unifies the result. This is the move prime° already makes in (aux kanren arith), used for a stronger reason: there, the guard is an optimisation over a relation that would merely be slow; here, in the ground-instant direction, it is the difference between the relation existing and not existing.

;; LAYER 1 -- pure.  No project°.  Every mode, a few milliseconds.
(define-relation (before° t u) (<° t u))
(define-relation (shift° t d u) (plus° t d u))

;; LAYER 2 -- the seam, project°-guarded.  t = d*86400 + sod.
;; The `else' branch IS the pure definition, and it is sound, complete and
;; productive -- at small magnitudes.  The guard adds two fast paths over it
;; and changes NO answer in any mode; it only changes the clock.
(define-relation (day+second° t d sod)
  (project° ((t* t) (d* d) (s* sod))
    (let ((T (numeral->number t*)) (DS (numerals->numbers (list d* s*))))
      (cond
        (T   ...)   ; escape: /° of an instant by 86400 does not terminate
        (DS  ...)   ; escape: *° at this magnitude costs seconds
        (else (fresh° (p) (<° sod DAY) (*° d DAY p) (plus° p sod t)))))))

What the guard costs the caller is a MODE OBLIGATION, and it is stated in the cases rather than assumed: because the branch is chosen by looking at instantiation at the moment the goal runs, conjunction ORDER is now part of the meaning. A goal that grounds t must be written before iso°, not after it. Groundness is decided by numeral->number, positive typing over the cells rather than (not (var? x)), so a half-built numeral like (1 0 . β) is correctly NOT taken for ground and falls to the open branch instead of being decoded as though its tail were empty.

The seam, and why weekdays stride

One relation crosses between the two magnitudes, day+second°, and it is the only place in the module where 86400 is written. Everything calendrical sits above it and never sees a 31-bit number again: civil°, day-of-week°, the seven weekday names and the window relations all speak DAY-COUNTS. That is the load-bearing decision. At 15 bits the open fallback of a guarded relation costs a millisecond an answer, so "neither side ground" ENUMERATES REAL DATES instead of being undefined; at 31 bits the same fallback would have to walk two billion seconds.

Weekday enumeration is the headline feature and it is a STRIDE precisely so that it never needs the modulo that would need that division. A weekday is not computed by dividing a day-count by seven -- /° on a day-count was measured at 2.9 s, and multiple° as a divisibility test gave no answer at all after three minutes on a negative case. Instead each weekday has an ANCHOR, the smallest day-count carrying it, and the generator is repeated addition from there:

;; 1970-01-01 is day 0 and a THURSDAY -- verified below against
;; (chicken time posix), which is the one fact no relation can witness for itself.
;; So the first Monday of the epoch is day 4 = 1970-01-05 = unixtime 345600.
(define weekday-epoch-day '#(3 4 5 6 0 1 2))   ; sunday .. saturday

;; GENERATOR ONLY: with x fresh, strictly increasing, ~1 ms an answer.
;; With x ground and OFF the stride it steps past x forever -- measured.
(define-relation (stride° base step x)
  (cond°
    ((=° x base))
    ((fresh° (next) (plus° base step next) (δ° (stride° next step x))))))

;; The same progression with a ground CEILING, and the ceiling is the whole
;; reason it terminates on a MISS.  That is what a test needs.
(define-relation (stride/≤° base step hi x)
  (cond°
    ((=° x base) (<=° base hi))
    ((fresh° (next) (plus° base step next) (<=° next hi)
             (δ° (stride/≤° next step hi x))))))

Both relations are pure layer 1, and the cases pin the difference between them, because it is the difference between an enumeration and a decision procedure. day-of-week° takes the other way out for its test direction: with the day-count ground it never strides at all, it escapes, which is why (monday° 20370) and the first four Mondays cost the same nothing.

Reading the expected values

Every expectation was read off a real run, and several of them are written in an order that is not the calendar's. cond° is or° and or° INTERLEAVES, so a dense enumeration comes out permuted: a four-second span° answers 400, 401, 403, 402, and stride/≤° answers 4, 11, 25, 18 where stride° answers 4, 11, 18, 25. Sorting those expectations would hide from a reader the one thing they must know before building a calendar on top of the module, which is that chronology is their job and not the solver's.

Queries ask for more answers than exist wherever the stream is meant to close, so the assertion pins EXHAUSTION and not merely correctness -- a four-second window asked for nine answers hands back four. And an expectation of '() is never decoration. A relation that cannot decide a negative case does not fail, it diverges, and a diverging case prints nothing at all, because the suite reports only once every case has finished. So each '() below is the assertion that a miss TERMINATES: that (monday° thursday-day-count) refuses instead of striding past it forever, that an inverted window is empty instead of silently swapping its bounds, and that a date which does not exist has zero solutions instead of a neighbour's.

A handful of modes are therefore deliberately absent, each named in the case that would have carried it: within° with a fresh middle, stride° as a test, a comparison with its LATER side fresh, and leap-year° on 1900. They diverge, or they answer an infinite family, or -- for 1900 -- they answer correctly for the wrong reason, the epoch floor rather than the century rule; and a suite cannot assert a hang. Where a mode is dropped the prose says what it does instead, and the closing form that answers the same question is tested in its place.
